# Leaf — 이미지 보호 기술 검증 보고서

> 목적: "이미지 복사·캡처 방지"가 실제로 어디까지 가능한지 실측 검증하고,
> Cloudflare 무료 티어에서 적용 가능한 아키텍처를 확정한다.
> 검증일: 2026-08-01 | 검증 대상: `prototype/` (Express + sharp)
> 관련 문서: [`01-기능명세.md`](./01-기능명세.md)

## 1. 결론 요약 (TL;DR)

| 항목 | 결과 |
|---|---|
| 웹에서 캡처를 "완전히" 막기 | ❌ **불가능** (OS 레벨 동작) |
| 캡처를 어렵게 + 품질 저하 + 추적 | ✅ 가능 |
| **서버 사이드 워터마크 (가장 강력)** | ✅ 실측 통과 — DevTools로 제거 불가 |
| 사용자 식별 워터마크 | ✅ 구현 가능 (유출 시 추적 가능) |
| 원본 이미지 격리 | ✅ 필수 — 미보호 시 원본이 그대로 노출됨 (실제 발견 사례) |
| Workers 무료 티어에서 실시간(온더플라이) 워터마크 합성 | ⚠️ **CPU 10ms 제한 초과** → 업로드 시 사전 처리로 전환 |

> 핵심: **"막는 것"이 아니라 "유출해도 쓸모없게 + 추적 가능하게"** 하는 것이 목표.
> 그리고 Cloudflare 무료 티어 한계(요청당 CPU 10ms)가 아키텍처를 결정한다.

## 4. 검증 항목 & 결과

### 4.1 서버 사이드 워터마크 — 합성 확인 ✅

**방법**: 원본 1600×1067 이미지와 `uid=test-user@leaf.com` 워터마크 합성본을
픽셀 단위(raw)로 비교.

**결과**:

```
변화 픽셀: 218,196 (12.78%)
평균 변화량: 7.73  (최소 1, 최대 34)
→ 저투명도(4~6%) 흰색 텍스트 패턴의 정상적인 합성 확인
```

- 워터마크가 **이미지 픽셀에 직접 구워짐** → 브라우저 DevTools·CSS 오버레이 제거로는 절대 안 지워짐
- 사용자 UID·날짜를 넣으면 **유출본에서 유포자를 추적 가능**
- 응답 헤더 `Cache-Control: no-store, no-cache, must-revalidate` ✅ (브라우저 로컬 캐시 방지)

### 4.2 원본 직접 접근 — 미보호 시 취약 (실제 발견) ❌→✅

**발견**: 프로토타입 v1에서 `photos/` 폴더가 `express.static`으로 서빙되어
**URL만 알면 원본(워터마크 없는)이 그대로 다운로드**됐다.
`/photos/01.jpg` → `200 OK` (워터마크 우회 가능).

**조치**: static 서빙 전에 `/photos/` 차단 미들웨어 배치 → `404`.
경로 변형 시도(`/photos/01.jpg/`)도 `404`. ✅

> **설계 원칙**: 원본은 절대 정적 서빙 금지. R2 private 버킷 + Workers 인증 게이트 경유만.
> 이 취약점은 "캡처 차단"보다 더 심각한 문제로, 실제 구현 시 최우선 방어.

### 4.3 보안 헤더 — 적용 순서 버그 발견 ❌→✅

**발견**: 프로토타입 v1에서 보안 헤더 미들웨어가 `express.static` 뒤에 있어
**정적 파일(HTML 포함)에는 헤더가 전혀 적용되지 않았다** (X-Frame-Options 등 부재).

**조치**: 헤더 미들웨어를 static 앞으로 이동 + `app.disable('x-powered-by')` + `Permissions-Policy` 추가.

**수정 후 실측**:
```
HTTP/1.1 200 OK
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Permissions-Policy: camera=(), microphone=(), geolocation=()
```
정적 파일·API 모두 적용 확인 ✅

### 4.4 캡처 알림 수집 — 동작 ✅

```
POST /api/capture-alert {page, image, detail:'contextmenu', userAgent} → {"ok":true}
GET  /api/capture-log → 저장된 로그 (ip, userAgent 포함)
```
- 클라이언트에서 `keepalive:true`로 전송 → 페이지 닫힘에도 도착
- **주의**: 이 알림은 "징후 추정"이지 "실제 캡처 감지"가 아님 (오탐 다수). 운영 시 알림 지양, 로그 축적용.

### 4.5 합성 성능 — Workers CPU 10ms 제한 대비 ⚠️

**실측 (1600×1067 JPEG, 로컬)**:

```
run1: 총 205ms   run2: 77ms   run3: 78ms
```

- 로컬 Mac에서도 **80~200ms** 소요
- Cloudflare Workers 무료 티어는 **요청당 CPU 10ms 상한** → 초과 시 요청 실패
- `sharp` WASM 구동이라도 대형 이미지 디코딩+합성+인코딩은 제한 초과가 현실적

> **결정**: 워터마크 합성을 **요청 시점(on-the-fly)에 하지 않고,
> 업로드 시점에 미리 생성(pre-composite)해 R2에 저장**한다.
> (기능 명세 §9.3, §11 참조)

### 4.6 클라이언트 사이드 차단 — 동작 검증 (코드 검토 + 표준 지식)

| 기법 | 데스크톱 | iOS | Android | 비고 |
|---|---|---|---|---|
| 우클릭 차단 | ✅ | - | ✅ | `contextmenu` preventDefault |
| Ctrl/Cmd+P 차단 | ✅ | ❌(Safari 인쇄 메뉴) | ✅ | `keydown` preventDefault |
| 드래그/긴 누르기 금지 | ✅ | ✅ | ✅ | `user-select:none`, `touch-callout:none` |
| PrintScreen 키 차단 | ⚠️ | ❌ | ⚠️ | **`keydown`으로 OS 캡처를 막을 수 없음** (이벤트가 JS에 도달하지 않거나 무시됨) |
| DevTools 감지 (창 크기 변화) | ⚠️ | - | ⚠️ | 우회 가능, 일반 사용자만 해당 |
| visibilitychange (앱 전환) 감지 | - | ⚠️ | ⚠️ | **화면 캡처 버튼은 감지 불가**, 오탐 큼 |
| iOS/Android 화면 녹화 감지 | ❌ | ❌ | ❌ | **웹 API 없음** |

**요약**: 브라우저(JS)는 "사용자가 스크린샷을 찍는 순간"을 **기술적으로 감지할 수 없다**.
(인스타그램 등은 OS 네이티브 API를 쓰는 앱이기에 가능. 웹은 불가.)
따라서 클라이언트 기법은 **우발적 저장 방지** 수준이며, 핵심은 서버 워터마크다.

## 6. Cloudflare 아키텍처에서의 보호 설계 (확정)

```
[업로드 시 — 오프라인 사전 처리]
원본 ─→ R2 origin/ (private, 절대 서빙 금지)
       ├─→ 리사이즈(≤1600px) + 워터마크 합성 ─→ R2 webview/ (private)
       └─→ 썸네일(300px) ─→ R2 thumb/

[열람 시 — 요청당 CPU 10ms 내]
브라우저 → GET /api/albums/{id}/pages/{no}
  ├─ 세션(Upstash) 검증
  ├─ 권한 평가 (무료/결제/관리자)
  ├─ R2 webview 이미지 단순 읽기 (합성 없음 → CPU 수 ms)
  └─ 응답: Cache-Control private + ETag
```

| 계층 | 방어 내용 | 무료 티어 적합 |
|---|---|---|
| 원본 격리 | private R2 + 인증 게이트 | ✅ |
| 서버 워터마크 | 사전 합성본만 서빙 (UID/날짜 포함) | ✅ CPU 문제 없음 |
| 클라이언트 오버레이 | 뷰어에 세션 UID 반복 표시 (스크린샷에 포함) | ✅ |
| 입력 차단 | 우클릭·인쇄·드래그 | ✅ |
| 헤더/CSP | X-Frame-Options, nosniff, CSP | ✅ |
| Rate limit | Upstash 기반 | ✅ |
| 관리자 보안 | IP 화이트리스트 + TOTP 2FA | ✅ |

## 7. 오픈 리스크 & 한계

1. **유출 후 추적은 가능하지만 예방은 불가** — 고의 유출자가 스크린샷을 찍으면 막을 수 없다.
   워터마크로 유포자를 특정해 제재하는 것이 현실적 대응.
2. **워터마크 해상도/품질** — 4~6% 투명도는 읽기는 가능하나 고의로 잘라낼 수 있음.
   핵심 정보(UID)는 반복 배치 + 모서리 포함으로 내성 강화 권장.
3. **원본 해상도 노출** — 웹뷰 해상도(1600px) 이상을 주지 않아야 원본과의 차별화 유지.
4. **CSP 인라인 스크립트** — 기능 명세 §10.1의 CSP는 인라인 스크립트를 금지하므로,
   프로토타입의 `<script>`는 빌드 시 외부 파일로 분리 필요 (Pages 배포 시 자연 해결).
5. **이미지 포맷** — 웹뷰는 WebP/AVIF로 인코딩해 용량·품질 최적화 권장
   (브라우저 지원: AVIF는 iOS 16+, Android Chrome 85+).
6. **캐시와 권한 충돌** — 유료 해제 전후 이미지를 엣지에 오래 캐시하면 권한 우회 가능.
   `Cache-Control: private` + 짧은 `s-maxage` 또는 캐시 키에 세션 포함.

## 8. (참고) Workers Paid로 전환 시 개선 옵션

무료 티어에서는 사전 처리 방식이 정답이지만, 수익이 나서 Workers Paid(월 $5)로
전환하면 **사용자별 온더플라이 워터마크**를 쓸 수 있다 (CPU 30만 ms/월 확보).

- `sharp` WASM 또는 `@cloudflare/images` 대안 검토
- 이 경우에도 원본(private) + 웹뷰(합성) 이중화 원칙은 유지
- 업그레이드 시 메모리/CPU 예산 재측정 필수 (요청당 최대 CPU 제한 설정 가능)

## 10. 결론

1. **캡처는 100% 차단 불가** — OS 레벨. "억제 + 추적"이 목표여야 함.
2. **서버 사이드 워터마크가 유일한 확실한 방어선** — 실측 검증 완료.
3. **원본 격리는 필수** — 미적용 시 워터마크가 무의미해짐 (실제 취약점으로 확인).
4. **Cloudflare 무료 티어 CPU 10ms 제한** → 워터마크는 업로드 시 사전 합성(프리-컴포지트).
5. 클라이언트 기법(우클릭·단축키·DevTools 감지)은 **보조 수단** — 우발적 저장 방지 + 유출 추적.
