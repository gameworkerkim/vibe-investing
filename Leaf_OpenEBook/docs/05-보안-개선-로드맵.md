## 0. 한 줄 요약

**현재 추적 체계는 "스크린샷을 찍는 순진한 열람자"만 식별한다.**
워터마크·LSB가 전부 브라우저 JS에서 붙기 때문에, 이미지 URL을 직접 요청하면
신원 정보가 **하나도 없는** 원본이 그대로 나온다. 대량 유출자는 추적 불가.

## 2. 위협 시나리오

### S1. URL 직접 수집 (현재 완전 무방비) — 심각도 **치명적**

```
1. 뷰어를 열어 DevTools Network에서 이미지 URL 패턴 파악
   → /Leaf/api/albums/1/pages/{n}
2. 반복문으로 1..N 순회 (쿠키·Referer 불필요)
3. 원본 해상도 1600px 이미지 확보
```

- 현재 방어: **없음**
- 남는 흔적: **없음** (capture_alerts 미기록, 신원 WM·LSB 부재)
- 결론: **추적 불가**. 유출본에는 공통 문구뿐이라 열람자를 특정할 수 없다.

### S2. JS 비활성화 열람 — 심각도 **치명적**

canvas 베이크·LSB·CSS 오버레이가 전부 클라이언트 JS다. JS를 끄면
`<img>`가 서버 원본을 그대로 표시하며, 우클릭 차단·캡처 알림도 함께 죽는다.

### S3. OS 스크린샷 (설계상 상정한 주 시나리오) — 심각도 **낮음 (방어 유효)**

- 신원 시각 WM은 픽셀에 구워져 있어 **남는다** → 추적의 유일한 실효 수단.
- LSB는 재압축으로 소실 → 보조 수단으로도 기대 불가.
- 잔여 약점: 워터마크 격자의 x 오프셋이 모든 행에서 동일하므로
  **세로 띠 크롭 한 번으로 모든 행에서 같은 구간(예: IP)이 통째로 제거**된다.

### S4. 로그 위조로 무고한 사용자 프레이밍 — 심각도 **높음**

```bash
curl -X POST .../Leaf/api/capture-alert -d '{"sessionId":"...","email":"victim@..."}'
```

임의 sid·email을 서버가 그대로 저장한다. 캡처 로그는 **증거 능력이 없고**,
반대로 타인을 유출자로 몰기 위한 도구가 될 수 있다. 무제한 쓰기이므로 D1 비용 공격도 가능.

### S5. 열람자 개인정보 역유출 — 심각도 **높음**

`GET /Leaf/api/capture-log`이 공개되어 모든 열람자의 IP·email·sessionId가 노출된다.
또한 IP를 워터마크에 각인하므로, 유출본이 SNS에 퍼지면 **열람자 IP가 함께 공개**된다.

## 4. 수정 로드맵

### 단계 1 — 접근 통제 (P0, 최우선)

> 이 단계 없이는 아래 워터마크 작업이 모두 장식에 불과하다.

1. **이미지 게이트에 세션 필수화** — `leaf_sid` 쿠키 없는 요청은 403.
2. **서명 URL 도입** — `/api/albums/{id}/pages/{n}?exp=&sig=`
   (HMAC(sessionId + key + page + exp), TTL 60~120초). 메타 응답에서 발급.
3. **레이트리밋** — D1 또는 Durable Object 기반, 세션·IP당 분당 N장 초과 시 429 + 알림 기록.
4. **`capture-log` 관리자 인증** — Cloudflare Access 또는 헤더 토큰.
5. **`capture-alert` 서버 신뢰 소스 사용** — 클라이언트가 보낸 sid/email 폐기,
   쿠키·`CF-Connecting-IP`에서 서버가 직접 채운다. 세션당 쓰기 상한 부과.

**수용 기준**: 쿠키 없는 `curl`로 페이지 1장도 받을 수 없다. 25장 순회 시 429가 발생한다.

### 단계 2 — 서버 측 신원 워터마크 (P0-2 / P1)

Workers 무료 티어 CPU 10ms로는 요청마다 합성이 불가능하다. 현실적 대안 두 가지:

| 방식 | 개요 | 장점 | 단점 |
|---|---|---|---|
| **A. 변형 배정** (권장) | 워터마크 위치·오프셋이 다른 변형 N개(예: 64)를 업로드 시 사전 생성, 사용자↔변형을 결정적으로 매핑. 페이지별 변형 조합이 지문이 됨 | 런타임 합성 비용 0, 무료 티어 유지, 크롭에 강함 | 저장 용량 N배, 식별 해상도가 조합 수에 한정 |
| **B. 최초 열람 시 1회 합성 후 R2 캐시** | 로그인 사용자별 합성본을 첫 요청 때 생성해 캐시 | 사용자 단위 정확 식별 | 합성 실행 환경 필요(Queue/Container/외부 워커), 저장 증가 |

단계 2에서는 **A를 먼저 도입**하고, 로그인(P3) 도입 시 B로 승격하는 경로를 권장한다.
클라이언트 canvas 베이크는 서버 워터마크의 **보조**로만 유지한다.

### 단계 3 — 워터마크 견고성 (P1)

1. 격자 오프셋을 **행마다 의사난수로 시프트** → 세로 크롭 내성 확보.
2. 식별자에서 **IP 제거**, `sid` 8자 + 짧은 사용자 코드로 대체(개인정보 노출 축소).
   IP는 서버 로그에만 보관하고 사후 조회로 연결.
3. LSB 정책 결정 — **둘 중 하나**:
   - DCT/주파수 영역 워터마크로 교체(재압축 내성 확보), 또는
   - 유지하되 문서를 "PNG 무손실 저장에만 유효"로 정정하고 보조 수단으로 격하.

### 단계 4 — 결함·비용 (P2)

1. 캔버스 크기 계산을 computed style 복사에서 **직접 계산**으로 변경, `resize`·`orientationchange`에서 재계산.
2. 캐시버스터 제거, `ETag`/조건부 요청 활용.
3. 서빙 해상도를 표시 크기에 맞춰 축소(예: 장변 900px), 원본은 R2에만 보관.
4. `visibility spike` 임계값 재조정 또는 단독 알림 폐기(교차 확인 신호로만 사용).

## 5. 회귀 검증 체크리스트

```bash
# 1) 쿠키 없는 직접 요청 차단
curl -o /dev/null -w "%{http_code}\n" ".../Leaf/api/albums/1/pages/2"      # 기대: 403

# 2) 레이트리밋
for i in $(seq 1 25); do curl -s -o /dev/null -w "%{http_code} " ".../pages/$i"; done  # 기대: 429 포함

# 3) 관리자 로그 보호
curl -o /dev/null -w "%{http_code}\n" ".../Leaf/api/capture-log"           # 기대: 401/403

# 4) 알림 위조 차단
curl -X POST .../Leaf/api/capture-alert -d '{"email":"victim@example.com"}' # 기대: 저장 시 email 무시
```

- [ ] 정상 뷰어 경로에서 이미지 정상 표시 (모바일·태블릿·데스크톱, 회전 포함)
- [ ] 서버 합성 워터마크에 신원 문자열 포함
- [ ] 세로 40% 크롭 후에도 식별자 판독 가능
- [ ] `capture_alerts`의 sid/email이 서버 유래값과 일치
