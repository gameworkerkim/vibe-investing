循环工程为何会失败?

발행 2026.07.15 · 주제 UI · 개발도구 · Loop

🇰🇷 한국어 English 日本語 中文

在大厂'像用水一样消耗token'的神话背后,隐藏着阻碍循环工程成为通用解决方案的三个结构性瓶颈:数据质量、行业领域知识缺口和不利的经济性。

大厂"像用水一样烧token"的神话,及其背后隐藏的三个结构性限制

近来,"循环工程(Loop Engineering)"在软件开发行业受到了极大关注。它指的是一种闭环(closed-loop)开发方式:AI生成代码(generate)、测试(test),甚至完成部署(deploy),再将其结果重新作为输入反馈回去。这是一种愿景——像拥有无限token的超大型AI组织一样,在最小化人工介入的情况下让产品无限进化。

但现实并非如此。迄今为止,被认为通过循环工程取得有意义成果的案例,大多局限于能够"像用水一样"消耗token的LLM公司,或是Google、Meta、Microsoft这类大型科技公司。而在产业一线,从零基础开始并真正落地到实际生产服务的案例却很难找到。本专栏结合具体案例与参考文献,分析阻碍循环工程成为通用解决方案的三个决定性瓶颈。

1. 只属于"token富豪"的特权——缺乏完善的文档、测试与场景

要让循环工程发挥效果,必须有LLM能够理解的丰富文档、用户场景以及与数据库相关的测试代码作为支撑。而这只是数据基础设施雄厚的组织才拥有的特权。

成功案例——只有在整理好的数据之上才能运转的循环

大厂的成果无一例外都建立在"精心维护的内部数据"这一基础之上。

  • Google: 面向公司内部超过1万名开发者,历时3个月,在8种语言中应用了基于ML的代码补全(ML-Enhanced Code Completion)。结果显示,构建-测试的迭代时间(coding iteration time)减少了6%,上下文切换(context switch)减少了7%,建议采纳率(acceptance rate)达到25%~34%。但实际由ML编写的代码仅占全部代码的约3%[1]。也就是说,即便投入巨大资源,自动化的实际占比仍然有限——这一点是大厂自己证明的。
  • Meta: 将基于自家代码库训练的"CodeCompose"部署给1.6万名工程师,在15天内提供了450万次建议。建议采纳率为22%,开发者输入代码中的8%来自CodeCompose,定性反馈中91.5%为正面评价[2]。值得注意的是另一点:Meta在训练之前就有意过滤掉了"PHP风格"等过时模式,以及从未上线生产环境的实验性代码。正是因为人工事先对高质量数据进行了整理,循环才能够运转起来。
  • Microsoft/GitHub: 常被引用的"使用Copilot开发速度提升55%"这一数字,其确切来源并非Microsoft内部的整体应用结果,而是GitHub进行的对照实验(controlled experiment)。约95名专业开发者被分为两组,要求实现一个JavaScript HTTP服务器,结果使用Copilot的组平均耗时71分钟完成,比对照组(161分钟)快了55%(p=0.0017)[3]。但必须明确的是,这一结果是在"需求明确且具有普遍性的单一任务"这一理想条件下得出的。

现实的壁垒——在未经整理的环境中,bug会大量产生

中小规模组织或初创企业的情况则完全不同。在测试覆盖率低、文档不完善的环境中引入AI编程助手,反而会产生反效果——缺陷大量增加。一份具有代表性的报告显示,未经审查就采用的AI生成代码中,相当一部分(部分分析显示约48%)可能包含安全漏洞[4]。要让循环运转起来,首先需要用于验证该循环输出结果的"基准数据",而大多数企业并不具备这一条件,只是盲目追逐潮流,最终以失败告终。

简而言之,循环工程的第一道准入门槛并非模型性能,而是输入数据的质量,而这本质上是"token富豪"才拥有的特权。

2. 行业领域知识的盲区——即便是LLM也找不到最佳实践

要让LLM找到最优的实现模式,该领域的代码和架构必须在预训练(pre-training)数据中得到充分体现。像Web、移动应用这类普遍性领域在GitHub上资源丰富,但制造业、金融、医疗等特殊行业的核心逻辑在公开数据中几乎不存在。

具体的局限案例——在业务逻辑面前崩溃的转换

遗留代码现代化是最能清晰暴露这一局限的领域。COBOL至今仍是处理全球约70%银行交易的关键任务(mission-critical)资产[5]。

  • 通用LLM的局限: 在一项实务比较分析中,将COBOL程序转换为Java的任务交给通用工具GitHub Copilot后,得到的是缺乏对业务逻辑和系统上下文理解的"表面转换"。它遗漏了DB2集成,也未能识别控制新客户编号生成的NCS(Named Counter Server)的作用[6]。这表明,模型无法凭空创造出公开数据中不存在的领域规则。
  • 即便是专用工具,人工验证依然不可或缺: IBM推出了基于1.6万亿token训练、并用数千对COBOL-Java程序进行微调的专用模型(基于Granite 20B的watsonx Code Assistant for Z)[5]。然而2026年的一份实务评测仍明确指出,"不应期望在未经精炼(refinement)的情况下就能直接用于生产环境"。也就是说,即便使用专用工具,资深开发者的人工验证与语义等价性(semantic equivalence)测试依然不可或缺[6]。
  • 在领域逻辑上的持续失败: 在一项涉及约400名开发者的ZoomInfo案例研究中,Copilot在生成样板代码(boilerplate)方面表现出色,但在领域特定逻辑(domain-specific logic)上却举步维艰[3]。

如果没有能够指导准确行业知识的人类专家介入,循环只会收敛到看似合理却方向错误的结果。在监管严格的金融、医疗环境中,这一盲区带来的风险会更大。

3. 经济性的幻象——token成本与验证人力的双重账单

即便部分解决了第1项(数据)和第2项(领域知识)的问题,最后一道关口依然存在:让循环"持续运转"本身的成本。大厂能够像用水一样消耗token的原因很简单——它们拥有自己的基础设施,或者自身就是模型制造商。而普通组织每月都会收到账单。

第一张账单——失控的token成本

代理式(agentic)编程的成本远远高于普通的聊天或推理。

  • 一项研究发现,代理式编程任务消耗的token量比聊天/代码推理多约1,000倍,若算上重试和自我修正(self-correction)循环,每个任务可达100万至350万token[7][8]。
  • 更大的问题在于不可预测性。即便反复执行同一任务,token使用量的波动幅度也可达最多30倍,而且token用得多并不代表准确率会提高——准确率反而在中等成本区间达到峰值,超过该区间后趋于饱和。更糟的是,前沿模型自身也无法准确预测其token成本,并且系统性地低估了成本[8]。这使得制定预算这件事本身几乎无法成立。
  • 成本会直接体现在现金流上。Claude Code按开发者每个活跃使用日计费约13美元,若大力推进自动化,每位工程师每月的费用可能飙升至500至2,000美元[9]。当GitHub Copilot转为按token量计费后,开发者反映成本增加了10至50倍,运行代理会话的用户预计每月费用将达到750至3,000美元。此前依赖"氛围编程(vibe coding)"的非开发者群体受到的冲击最大[10]。

我自己为了高效使用token,也会根据用途选用不同的LLM,但最终得出的结论是:把烧token的这笔钱投资到AI巨头股票上,投资回报率(ROI)反而更高。归根结底,安全等需要留意的部分仍必须由人来审阅确认,而确实制作出LLM能够理解的文档才是更有效率的做法。

第二张账单——隐藏的验证人力成本

循环的输出结果不能被无条件信任。必须有人阅读、验证并修正它,而这笔成本往往会抵消掉节省下来的部分。

  • 非营利研究机构METR在2025年进行的一项随机对照试验(RCT)彻底颠覆了传统认知。16名熟练开发者在平均约100万行代码规模的成熟开源仓库中完成了246个真实任务,结果显示,使用AI工具时,他们的工作实际上慢了19%。但他们自己却认为速度提高了20%[11]。
  • 不过这一结果需要谨慎解读(不确定性标签:中)。METR自己在2026年的后续复审中承认存在选择效应(selection effect)的可能性,并正在修改实验设计;部分后续估算显示,效应大小已变为现有参与者-18%、新参与者-4%[12]。也就是说,不应将其解读为"AI总会拖慢速度"这一定律,而应视为一个强烈信号:在成熟的代码库中,验证负担可能会侵蚀生产力提升带来的收益。

综合——只有在大厂的账本上才能成立的ROI

归根结底,循环工程的投资回报率(ROI),只有在能以接近零边际成本获取token的大厂账本中才在一定程度上能够成立。而在普通组织中,(1)波动巨大的token成本与(2)始终无法减少的验证人力成本相加而成的"双重账单",将与并不保证一定发生的速度提升进行交换。如果对编程本身以及行业领域缺乏理解,最终只会陷入空转的无限循环。

三大瓶颈总结

结构性瓶颈 大厂为何能够通过 普通组织为何会失败
1. 输入数据(文档·测试·场景) 公司内部积累了大量经过整理、精心维护的代码、测试和场景(例如Meta对训练数据的预先过滤) 测试覆盖率与文档不足 → 缺乏验证基准,bug大量产生
2. 领域知识(行业特定逻辑) 可以直接用自家领域数据进行微调 制造业、金融、医疗的核心逻辑在公开数据中缺失 → 转换表面化、易出错
3. 经济性(token·验证成本) 拥有自有基础设施/模型 → token边际成本≈0 每任务100万~350万token,波动可达30倍,加上验证人力成本 → ROI不足

结论——循环是电动工具,而非自主运作的神谕

试图直接复制大厂循环工程成功经验的尝试,大多以失败告终。这是因为其成功的本质并非"优秀的AI模型",而是围绕该模型的三项基础设施性前提条件:经过整理的数据、积累的领域知识,以及边际成本近乎为零的token供给。在不具备这些前提条件的组织中,期待剥离人工介入的完全自动化循环,近似于一种试图用工具性能来弥补基础设施缺失的错觉。

"LLM是Excel,不是神谕。"正如Excel能加速计算却无法代替会计判断一样,循环也只是加速开发的电动工具,而非能够自主孕育出正确产品的神谕(oracle)。现实的策略并非追逐闭环神话,而是先建立起让人类始终留在验证环节(human-in-the-loop)的渐进式、部分自动化,并在此基础上不断积累数据与领域知识,逐步扩大循环的边界。
